## public/styles.css

This file is the hand-written CSS companion to Tailwind: it defines the actual color values as CSS custom properties (one block for light mode, one for dark mode), plus a handful of small utility classes, animations, and scrollbar styles that either aren't expressible in Tailwind's utility classes or are reused often enough to deserve a name. The theming strategy is a Material-Design-3-style token system — every color is defined twice (once under `:root, .light` and once under `.dark`) using the same variable names, so the rest of the app (and `tailwind-config.js`) never needs to know which mode is active; it just reads `var(--surface)`, `var(--on-surface)`, etc. `public/app.js` toggles the `dark`/`light` class on `<html>` (confirmed at `app.js:6-7,13-16`), which is what flips which block of variables is in effect. Below the variables, the file adds Material Symbols font settings, scrollbar theming, status/log-row helper classes, and several `@keyframes` animations used for loading and transition effects across the dashboard pages.

**Lines 1–51 — light theme variable block.** `:root, .light { ... color-scheme: light; }` defines the full Material-3-style token palette for light mode: error/on-error/error-container/on-error-container (lines 3–6), primary/on-primary/primary-container/on-primary-container (7–10), secondary and tertiary equivalents (11–18), the surface family — background, surface, surface-dim/bright, and the five surface-container-* elevation steps (19–29), on-surface/on-surface-variant/outline/outline-variant (30–33), inverse-* tokens for content that sits on an inverted background such as tooltips or snackbars (34–36), `surface-tint` (37), and the "fixed" color set — primary-fixed/-dim and their `on-*` pairs, repeated for secondary and tertiary (38–49). This is the standard Material 3 token naming scheme: each color role has a base value, an "on-" value for text/icons drawn on top of it, and often a "-container" variant for larger fill areas. `color-scheme: light` (line 50) tells the browser to render native form controls (scrollbars, checkboxes) in light style. Every one of these names reappears verbatim (as `var(--name)`) in the `colors` map of `tailwind-config.js`, which is how Tailwind utility classes like `bg-surface` or `text-on-surface-variant` resolve to these values.

**Lines 53–102 — dark theme variable block.** `.dark { ... color-scheme: dark; }` redefines the identical variable names with dark-mode values. The pairing is not a naive "invert the light value" — it's a genuine second palette tuned for dark backgrounds, e.g. `--background` goes from `#f8f9ff` (near-white) in light to `#020617` (near-black) in dark (line 19 vs 70), and `--primary` flips from a green (`#006c49`, line 7) to plain white (`#ffffff`, line 58) with `--on-primary` becoming a dark gray (`#2b3137`, line 59) — i.e. in dark mode the "primary" role is repurposed as a light accent against dark surfaces rather than staying a saturated brand green. `--surface-dim`/`--surface-bright` also swap roles: in light mode `surface-bright` is the lightest surface and `surface-dim` is slightly darker (22–23), while in dark mode `surface-dim` is the darkest surface and `surface-bright` is a lighter dark-gray (73–74) — consistent with Material 3's dark-theme elevation model where "brighter" surfaces sit higher in the stack. `color-scheme: dark` (line 101) switches native control rendering to dark. Because `.dark` and `.light`/`:root` share identical selectors' specificity for the same property names, whichever class is present on `<html>` wins by cascade order (`.dark` is declared after `:root, .light`, but `app.js` only ever has one of the two classes applied at a time via `classList.toggle`, so there's no real conflict in practice).

**Lines 104–108 — Material Symbols icon defaults.** `.material-symbols-outlined { font-variation-settings: 'FILL' 0, 'wght' 400, 'GRAD' 0, 'opsz' 24; vertical-align: middle; }` configures the variable-font axes for Google's Material Symbols icon font (FILL 0 = outlined/unfilled glyphs, weight 400, no grade adjustment, 24px optical size) and vertically centers icons relative to surrounding text/inline content — necessary because icon fonts default to baseline alignment, which looks misaligned next to text.

**Lines 110–116 — body defaults.** `body { background-color: var(--background); color: var(--on-background); font-family: 'Geist', sans-serif; overflow: hidden; }` applies the theme's background/foreground colors at the document root, sets the base sans-serif font to Geist (matching the `fontFamily` entries in `tailwind-config.js`), and sets `overflow: hidden` on the body — this is a deliberate choice for a dashboard app where individual panels (like the log stream) scroll internally via their own `overflow-y-auto` containers rather than the whole page scrolling.

**Lines 118–131 — scrollbar theming.** Three related blocks style WebKit scrollbars (Chrome/Edge/Safari; there's no Firefox `scrollbar-color` fallback here). The global `::-webkit-scrollbar` rules (119–122) set a 6px-wide/tall bar, a track colored with `--surface-container-lowest`, a thumb colored with `--surface-container-highest` with a 3px rounded radius, and a hover state using `--outline-variant` — i.e. the thumb is a subtle high-contrast rectangle sitting on the darkest/lightest surface tone with a low-emphasis outline color on hover. `.c-scroll` (124–127) is a "compact scroll" variant used on secondary panels: thinner (5px), transparent track, and a fully transparent-until-hover thumb using `--outline-variant`/`--outline`. `.log-stream` (129–131) is an even thinner (4px) scrollbar with the same transparent-track/outline-variant-thumb pattern, specifically for the log stream panel referenced by `id="log-stream"` in `dashboard.html` (confirmed at `dashboard.html:74`).

**Line 134 — log row hover.** `.log-row:hover { background-color: var(--surface-container-high); }` gives each log table/list row a subtle highlight on hover using one step up in surface elevation.

**Lines 137–144 — status badge.** `.status-badge { font-family: 'JetBrains Mono', monospace; padding: 2px 6px; border-radius: 2px; font-size: 10px; text-transform: uppercase; font-weight: 600; }` is the base style for the small log-level pill (e.g. "ERROR", "INFO") used in `logs-explorer.html` (confirmed at lines 364 and 387, where `status-badge` is combined with a per-level color class such as `${s.badge}`). It sets a monospace code font, tight padding, a small sharp-cornered radius, tiny uppercase bold text — the color itself is not set here, so it's supplied by whatever level-specific class is concatenated alongside it at render time.

**Lines 147–154 — surface card variants.** `.surface-card { background: var(--surface-container); border: 1px solid var(--outline-variant); }` is the standard bordered panel/card look. `.surface-card-low` (151–154) is a flatter variant: a lower-elevation `--surface-container-low` background with a fully transparent border (kept in the rule so the box model / layout doesn't shift if a real border is swapped in later), used where a card needs to recede rather than stand out.

**Lines 157–169 — pulse animations.** `.pulse-soft` (157–159) applies `pulse-soft 2s cubic-bezier(0.4, 0, 0.6, 1) infinite`, and the paired `@keyframes pulse-soft` (160–163) fades opacity between 1 and 0.7 at the midpoint — a gentle "breathing" effect for loading placeholders or live-status indicators. `@keyframes pulse-dot` (164–168) is a punchier variant that scales a dot between 0.95 and 1.1 while also fading opacity between 0.5 and 1, and `.animate-pulse-dot` (169) runs it on a 2s infinite loop — this is the classic "live/recording" dot pulse, distinct from `pulse-soft` in that it also animates `transform: scale(...)`, not just opacity.

**Lines 172–176 — log row level coloring.** Five rules each set a 2px left border keyed to log level: `.log-row-error` uses `var(--error)`, `.log-row-warn` a hardcoded amber `#f59e0b`, `.log-row-info` a hardcoded blue `#3b82f6`, `.log-row-debug` uses `var(--outline)`, and `.log-row-success` uses `var(--secondary)`. All five use `!important` to guarantee the border color wins over any Tailwind utility border classes applied to the same element. Notably, error/debug/success are theme-aware (they reference CSS variables and therefore change with light/dark mode), while warn and info are fixed hex colors that do not adapt to the theme — an inconsistency worth knowing about if a future dark-mode audit is done. These classes are generated dynamically: `app.js:77` has a helper that returns `` `log-row-${lvl}` `` to pick the right class per log entry.

**Lines 179–181 — drawer transition.** `.drawer-transition { transition: transform 0.3s cubic-bezier(0.4, 0, 0.2, 1); }` is a reusable transition timing (Material's standard "ease" curve) intended for slide-in/out drawer or panel components animated via `transform`.

**Lines 184–192 — shimmer loading effect.** `.shimmer` (184–188) builds a moving-gradient skeleton-loading effect: a `linear-gradient(90deg, transparent, color-mix(in srgb, var(--surface-container-highest) 60%, transparent), transparent)` creates a soft highlight band using the modern `color-mix()` function to blend the theme's highest-elevation surface color at 60% opacity into transparency (so the shimmer band itself is theme-aware in both light and dark mode), sized at `200% 100%` and animated via `shimmer 2s infinite`. `@keyframes shimmer` (189–192) slides the `background-position` from `-200% 0` to `200% 0`, producing the left-to-right sweeping highlight typical of skeleton loaders.

**Lines 195–201 — fade-in animation.** `@keyframes fadeIn` (195–198) animates from `opacity: 0; transform: translateY(4px)` to `opacity: 1; transform: translateY(0)` — a subtle upward-fade entrance. `.animate-fade-in` (199–201) applies it over `0.2s ease-out`, intended for newly-inserted content (e.g. new log rows or toasts) appearing without an abrupt pop-in.

**Lines 204–215 — multi-line truncation utilities.** `.truncate-2` (204–209) and `.truncate-3` (210–215) are identical except for the clamp count: both set `display: -webkit-box`, `-webkit-box-orient: vertical`, and `overflow: hidden`, differing only in `-webkit-line-clamp` (2 vs 3). This is the standard (WebKit-prefixed, but broadly supported in all major engines today) technique for truncating text to a fixed number of lines with an ellipsis, used where Tailwind's built-in `line-clamp-*` utilities either aren't configured or a project-specific name was preferred.

## public/tailwind-config.js

This file is the runtime configuration for the Tailwind CDN/browser build (loaded via `<script src="tailwind-config.js">` before Tailwind itself, e.g. `dashboard.html:7`) and its entire job is to extend Tailwind's default theme so that utility classes resolve to the CSS custom properties defined in `styles.css`, rather than Tailwind's stock color palette. It does not define any raw colors itself — every `colors` entry is a `var(--...)` passthrough — which is what makes the light/dark theming automatic: Tailwind generates classes like `bg-surface` or `text-on-primary`, and the browser resolves the underlying CSS variable based on whichever of `.light`/`.dark` is active on `<html>`. Beyond colors, it also extends `borderRadius`, `spacing`, `fontFamily`, and `fontSize` with a small set of project-specific design tokens (again matching names referenced elsewhere, e.g. `font-code-sm` used in `dashboard.html:74`).

**Lines 1–2 — config root and dark mode strategy.** `tailwind.config = { darkMode: "class", ...}` sets Tailwind's dark-mode variant to class-based rather than the `prefers-color-scheme` media-query default. This is what allows `dark:` variant utilities (e.g. `dark:bg-surface`) to be controlled explicitly by the `dark` class that `app.js` toggles on `<html>`, instead of following the OS-level setting automatically.

**Lines 3–4 — theme.extend wrapper.** `theme: { extend: { ... } }` — using `extend` (rather than replacing `theme` wholesale) means all of Tailwind's default scales (default color palette, spacing scale, font sizes, etc.) remain available; the entries below are added on top as new named options.

**Lines 5–53 — colors map.** This is a flat object mapping semantic color names to `var(--...)` CSS variable references, one-to-one with the custom properties defined in `styles.css` lines 1–101. It covers: background/on-background (6–7); the full surface family — surface, surface-dim, surface-bright, and the four surface-container-* elevation steps plus surface-container-lowest (8–15); on-surface/on-surface-variant and inverse-surface/inverse-on-surface (16–19); outline/outline-variant and surface-tint (20–22); the primary/secondary/tertiary triads each with their base, on-, and container variants plus inverse-primary (23–35); the full set of "fixed" tokens for primary/secondary/tertiary, each with fixed/-dim/on-fixed/on-fixed-variant (36–47); surface-variant (48); and the error family — error/on-error/error-container/on-error-container (49–52). Because every value here is a `var()` reference rather than a literal color, this map never needs to change between light and dark mode — the indirection through CSS variables is what makes a single Tailwind config serve both themes. This also means Tailwind class names exactly mirror the CSS variable names (minus the `--` prefix), e.g. `--surface-container-high` becomes usable as `bg-surface-container-high` or `border-surface-container-high`.

**Lines 54–59 — borderRadius scale.** `DEFAULT: "0.125rem"`, `lg: "0.25rem"`, `xl: "0.5rem"`, `full: "0.75rem"` define a compact, low-radius corner scale (2px/4px/8px/12px) that's notably sharper/smaller than Tailwind's stock radius scale — consistent with the tight, data-dense dashboard aesthetic seen elsewhere (e.g. the 2px radius on `.status-badge` in `styles.css:140`). Note that `full` here is overridden to `0.75rem` (12px), not Tailwind's usual "fully round" `9999px` — so `rounded-full` in this project produces a 12px rounded corner, not a circle/pill, which is a meaningful deviation from Tailwind defaults that any usage of `rounded-full` in the markup should account for.

**Lines 60–67 — spacing scale.** A small set of named spacing tokens: `unit: "4px"` (base grid unit), `gutter: "12px"` (presumably inter-column/inter-panel gap), `panel-padding: "16px"` (standard panel inner padding), `stack-compact: "4px"` and `stack-default: "12px"` (vertical rhythm between stacked elements, tight vs normal), and `margin-safe: "24px"` (a larger safe-area margin, likely for page edges). These become usable as e.g. `p-panel-padding` or `gap-gutter`, giving the layout a small named vocabulary on top of Tailwind's numeric spacing scale rather than relying purely on arbitrary pixel/rem multiples.

**Lines 68–75 — fontFamily scale.** Six named font-family tokens, all mapping to one of two actual font stacks: `headline-lg`, `headline-md`, and `body-md` all map to `["Geist", "sans-serif"]` (matching the `body` font in `styles.css:114`), while `code-md`, `code-sm`, and `label-caps` all map to `["JetBrains Mono", "monospace"]` (matching `.status-badge`'s font in `styles.css:138`). Despite three names per stack, only two physical fonts are in use — the extra names exist so that font-family and font-size/weight can be bundled together semantically (see next block) rather than because there are more distinct typefaces.

**Lines 76–83 — fontSize scale (paired with line-height/letter-spacing/weight).** Each entry pairs a pixel size with a config object of `lineHeight`, and sometimes `letterSpacing` and `fontWeight`, effectively defining full named type-scale "styles" rather than bare sizes: `headline-lg` is `30px/36px` with `-0.02em` tracking and `600` weight (23–24 in the file, i.e. lines 77); `headline-md` is `24px/32px`, `-0.01em`, `600` (78); `body-md` is `14px/20px`, weight `400`, no letter-spacing override (79); `code-md` is `13px/20px`, weight `400` (80); `code-sm` is `12px/18px`, weight `400` (81); and `label-caps` is `11px/16px` with `0.05em` positive tracking (letterspacing spread out, appropriate for small uppercase labels) and weight `600` (82). Combined with the matching `fontFamily` entries of the same name, a class like `font-headline-lg` alone won't set weight/tracking/line-height — those come from using the paired `text-headline-lg` font-size utility, so the two token sets (`fontFamily` and `fontSize`) are designed to be used together under matching names (e.g. `font-headline-lg text-headline-lg`) to get a complete, consistent typographic style.
