## Dockerfile

This file defines the container image used to build and run the log-ingestion service (it is what `docker-compose.yml`'s `app` service builds from, and what CI builds via `docker compose up --build`). It is a single-stage image: install dependencies, copy the source, and run the TypeScript entrypoint directly with `tsx` rather than compiling to `dist/` first. There is no multi-stage build or production pruning step — the image ships `devDependencies` (including `tsx` and `typescript`) alongside runtime dependencies.

- **Line 1**: `FROM node:20-alpine` — bases the image on Node.js 20 built on Alpine Linux, a minimal musl-libc distribution. Alpine keeps the image small compared to the default Debian-based Node images, at the cost of occasional native-module compatibility issues (not relevant here since the only native-ish dependency is `pg`, a pure-JS driver).
- **Line 3**: `WORKDIR /app` — sets `/app` as the working directory for all subsequent instructions (`COPY`, `RUN`, `CMD`), and creates it if it doesn't exist.
- **Line 5**: `COPY package*.json ./` — copies `package.json` and `package-lock.json` (the `*` glob matches both) into `/app` before copying the rest of the source. This is a deliberate Docker layer-caching optimization: as long as these two files don't change, the next `RUN npm ci` layer can be cached even if application source changes.
- **Line 6**: `RUN npm ci` — installs dependencies from the lockfile exactly as pinned (unlike `npm install`, `npm ci` refuses to modify `package-lock.json` and deletes `node_modules` first), giving reproducible builds. Because no `--omit=dev` flag is passed, this installs both `dependencies` and `devDependencies`.
- **Line 8**: `COPY . .` — copies the rest of the build context (the whole repo, minus anything excluded by `.dockerignore`) into `/app`, overlaying the `node_modules` already installed in the previous layer.
- **Line 10**: `EXPOSE 8080` — documents that the container listens on port 8080. This is metadata only (it doesn't actually publish the port); the real port mapping happens in `docker-compose.yml`'s `ports:` key. It matches the hardcoded `const PORT = 8080;` in `src/index.ts`.
- **Line 12**: `CMD ["npx", "tsx", "src/index.ts"]` — the container's default command: runs the TypeScript entrypoint directly through `tsx` (a fast esbuild-based TypeScript runner) rather than first compiling with `tsc` and running plain Node. Using `npx` here is redundant since `tsx` is already a project dependency reachable via `node_modules/.bin`, but it works because `npm ci` installed it locally and `npx` will find and run the local binary without a network fetch.

## docker-compose.yml

This file orchestrates local development and CI runs of the whole stack: the Node.js application container (`app`) plus a TimescaleDB/PostgreSQL container (`db`) it depends on. It wires environment variables the app reads at startup, maps ports for local access, defines a health check so the app only starts once the database is actually ready to accept queries, and caps each container's CPU/memory and tunes Postgres for write-heavy ingestion. This is also the file CI's `docker compose up --build -d` step uses directly, so it is the source of truth for how the service is configured in the CI environment.

- **Line 1**: `services:` — top-level Compose key declaring the set of containers this file manages.
- **Line 2**: `app:` — the name of the first service, the log-ingestion Node.js server.
- **Line 3**: `build: .` — tells Compose to build this service's image from the `Dockerfile` in the current directory (the repo root), rather than pulling a pre-built image.
- **Lines 4-5**: `ports: / - "8080:8080"` — publishes container port 8080 to host port 8080, so the app is reachable at `http://localhost:8080` from outside the container (used by both CI's `curl` checks and local browser access to the dashboard).
- **Line 6**: `environment:` — begins the block of environment variables injected into the `app` container at runtime.
- **Line 7**: `RETENTION_DAYS: 30` — configures how many days of logs the retention job (`src/services/retentionService.ts`) keeps before deleting older rows; read there as `process.env.RETENTION_DAYS` with a fallback of `"30"` if unset, so this line simply makes the default explicit here too.
- **Line 8**: `DB_HOST: db` — tells the app to connect to the Postgres/TimescaleDB container using the Compose service name `db` as the hostname, relying on Compose's built-in DNS for inter-container networking (matches `process.env.DB_HOST` read in `src/db/index.ts`).
- **Line 9**: `DB_PORT: 5432` — the port the app should use to reach Postgres *inside* the Compose network, i.e. the container's own listening port (Postgres's standard port), which is different from the host-mapped port below (`5433`). This value is read as `process.env.DB_PORT` in `src/db/index.ts`.
- **Line 10**: `DASHBOARD_PASSWORD: LogService2026!` — sets the single shared password used to log in to the dashboard (checked in `src/controllers/authController.ts` against `process.env.DASHBOARD_PASSWORD`). This has a default value defined in the compose file for local development; it should be overridden with a real secret in any non-local deployment.
- **Line 11**: `SESSION_SECRET: fts-intern-log-service-secret-key-2026` — the secret used by `express-session` (in `src/app.ts`) to sign the session cookie. This also has a default value defined in the compose file for local development and should not be reused as-is outside local dev.
- **Line 12**: `OPENAI_API_KEY: ${OPENAI_API_KEY:-}` — passes through the host's `OPENAI_API_KEY` environment variable if set, otherwise defaults to an empty string, using Compose's `${VAR:-default}` interpolation syntax. This is consumed by `src/services/supportService.ts`, which throws an error if the key is missing when the support-chat feature is actually invoked — so the app can still start without it, but that one feature will fail at call time.
- **Lines 13-15**: `depends_on: / db: / condition: service_healthy` — makes Compose wait until the `db` service's health check (defined below) reports healthy before starting `app`, rather than merely waiting for the container process to start. This avoids the app racing against a database that hasn't finished initializing yet — it's also why `src/index.ts` additionally polls with `waitForDb()` as a second line of defense.
- **Lines 16-17**: `cpus: 0.5 / mem_limit: 256m` — caps the `app` container to half a CPU core and 256MB of RAM. This mirrors the resource limits of the grading/benchmark environment this service is ultimately measured in, so local load testing (`load-test.js`) reflects those real constraints instead of running unrealistically fast on a developer's full-powered machine.
- **Line 19**: `db:` — the name of the second service, the database.
- **Line 20**: `image: timescale/timescaledb:latest-pg16` — uses the official TimescaleDB image built on PostgreSQL 16, pulled from a registry rather than built locally, providing the time-series extensions the log-ingestion schema relies on.
- **Lines 21-24**: `environment: / POSTGRES_USER: loguser / POSTGRES_PASSWORD: logpass / POSTGRES_DB: logdb` — these are the Postgres image's own bootstrap variables, used only on first container start to create the initial superuser, its password, and the default database. They must match what `src/db/index.ts` hardcodes (`user: "loguser"`, `password: "logpass"`, `database: "logdb"`) for the app to be able to authenticate. Note `POSTGRES_PASSWORD` here is a fixed local-development default baked into the compose file, not a production secret.
- **Lines 25-26**: `ports: / - "5433:5432"` — maps container port 5432 (Postgres's standard port) to host port 5433, letting a developer connect an external SQL client to `localhost:5433` without colliding with a Postgres instance already running on the host's default 5432.
- **Lines 27-28**: `volumes: / - pgdata:/var/lib/postgresql/data` — mounts the named volume `pgdata` (declared at the bottom of the file) onto Postgres's data directory, so database contents persist across `docker compose down`/`up` cycles instead of being wiped when the container is recreated.
- **Lines 29-33**: `healthcheck: / test: [ "CMD-SHELL", "pg_isready -U loguser -d logdb" ] / interval: 5s / timeout: 5s / retries: 5` — defines the health probe Compose uses for the `depends_on: condition: service_healthy` check above. It runs `pg_isready` (a Postgres CLI utility that checks whether the server accepts connections) for the `loguser`/`logdb` combination every 5 seconds, allowing up to 5s per attempt and up to 5 consecutive failures before marking the container unhealthy.
- **Lines 34-35**: `cpus: 1 / mem_limit: 1g` — caps the `db` container to one CPU core and 1GB of RAM, again mirroring the grading/benchmark spec's resource limits. In practice this makes `db` the bottleneck during sustained ingestion (it saturates its single CPU before `app` saturates its half-core-plus-event-loop budget), which is the realistic constraint this whole limits setup is meant to surface locally rather than only discovering it during grading.
- **Lines 36-45**: `command: / - postgres / - -c / - synchronous_commit=off / - -c / - shared_buffers=256MB / - -c / - max_wal_size=2GB / - -c / - checkpoint_completion_target=0.9` — overrides the image's default startup command to pass Postgres tuning flags directly (each `-c key=value` pair sets one `postgresql.conf` parameter). `synchronous_commit=off` stops the server from waiting for the WAL to be fsynced to disk before acknowledging a commit, trading a small durability window (a crash could lose the last few hundred ms of unflushed commits) for much lower per-commit write latency under heavy ingestion load. `shared_buffers=256MB`, `max_wal_size=2GB`, and `checkpoint_completion_target=0.9` raise Postgres's buffer cache and WAL headroom and spread checkpoint writes out over more of the checkpoint interval, reducing the I/O stalls that periodic checkpoints would otherwise cause during sustained writes.
- **Line 47**: `volumes:` — top-level key declaring named volumes usable by any service in this file.
- **Line 48**: `pgdata:` — declares the `pgdata` volume referenced by the `db` service, with no extra options, so Compose manages it with default settings (a local Docker-managed volume).

## .github/workflows/ci.yml

This GitHub Actions workflow is the project's continuous integration pipeline. It now runs in two phases: first a fast, container-free phase (install deps, typecheck, unit tests) that fails quickly on a type error or a broken validation rule without ever touching Docker, then the original build of the full Docker Compose stack, a wait for it to become healthy, and an end-to-end smoke test of the three core HTTP endpoints (ingest, query, aggregate) via real `curl` requests. It runs automatically on every push and pull request targeting `main`, and always tears the stack down afterward regardless of outcome.

- **Lines 1-7** (`name: CI` / `on: / push: / branches: [main] / pull_request: / branches: [main]`): names the workflow "CI" (as shown in the GitHub Actions UI) and triggers it on two events: a direct push to `main`, or a pull request whose target branch is `main`. This means feature-branch pushes alone don't trigger it — only opening/updating a PR against `main`, or pushing straight to `main`, does.
- **Lines 9-11** (`jobs: / build-and-test: / runs-on: ubuntu-latest`): defines a single job named `build-and-test` that runs on GitHub's latest Ubuntu-based hosted runner, which comes with Docker and Docker Compose preinstalled.
- **Step "Checkout code" (lines 14-15)**: `uses: actions/checkout@v4` — checks out the repository's contents into the runner's workspace so subsequent steps have access to the `Dockerfile`, `docker-compose.yml`, and source tree.
- **Step "Setup Node.js" (lines 17-20)**: `uses: actions/setup-node@v4` / `with: node-version: 20` — installs Node 20 directly on the runner (outside any container), needed for the two new steps below since typechecking and unit tests now run against the host's Node/`npm`, not inside the `app` Docker image.
- **Step "Install dependencies" (lines 22-23)**: `run: npm ci` — installs exactly the versions pinned in `package-lock.json` (unlike `npm install`, it won't update the lockfile), giving a reproducible `node_modules` for the next two steps.
- **Step "Typecheck" (lines 25-26)**: `run: npm run build` — runs `tsc --noEmit` (see `package.json` below); a type error anywhere under `src/` fails the job here, before Docker is ever invoked.
- **Step "Unit tests" (lines 28-29)**: `run: npm test` — runs `tsx --test src/**/*.test.ts` (currently just `src/services/logsService.test.ts`, covering `validateLogEntry`); a failing assertion fails the job here, again before the (much slower) Docker build/health-check/smoke-test steps run.
- **Step "Build and start services" (lines 31-32)**: `run: docker compose up --build -d` — builds the `app` image from the Dockerfile (picking up any code changes in this run) and starts both `app` and `db` in detached mode (`-d`); a broken Dockerfile or compose file fails the job here.
- **Step "Wait for services to be healthy" (lines 34-46)**: a shell loop (`for i in {1..30}`) that polls `http://localhost:8080/health` with `curl -sf` up to 30 times, 2 seconds apart (up to ~60 seconds total). `-s` silences progress output and `-f` makes curl fail (non-zero exit) on HTTP error codes, so a non-2xx response or connection refusal doesn't accidentally look like success. On the first successful health check it prints a success message and exits `0` immediately; if all 30 attempts fail, it prints a failure message, dumps `docker compose logs` for debugging, and exits `1` to fail the job — this verifies not just that the container started but that the app's own startup sequence (`waitForDb()` + `migrate()` in `src/index.ts`) completed and the server is actually listening.
- **Step "Test ingestion endpoint" (lines 48-52)**: `curl -f -X POST http://localhost:8080/logs -H "Content-Type: application/json" -d '{"logs": [...]}'` — sends a single well-formed log entry (timestamp, level, service, message) to the ingestion endpoint. The `-f` flag makes any non-2xx response fail this step, verifying the log-ingestion route accepts a minimal valid payload and returns success end-to-end (through routing, validation, and the database write).
- **Step "Test query endpoint" (lines 54-56)**: `curl -f "http://localhost:8080/logs?service=ci-test"` — queries logs filtered by `service=ci-test`, the same service name used in the log just ingested, verifying that a freshly-ingested log can be read back through the query API (i.e. the write actually landed in the database and the read path works).
- **Step "Test aggregate endpoint" (lines 58-60)**: `curl -f "http://localhost:8080/logs/aggregate?since=...&until=...&bucket=1h&group_by=service"` — hits the aggregation endpoint with a time range spanning the date the log was ingested (`2026-07-24`), a 1-hour bucket size, and grouping by `service`, verifying the aggregation/analytics query path also works against real data without erroring.
- **Step "Show logs on failure" (lines 62-64)**: `if: failure()` / `run: docker compose logs` — runs only if any previous step in the job failed, dumping all container logs to the Actions log to aid debugging a broken build or a failed endpoint check.
- **Step "Tear down" (lines 66-68)**: `if: always()` / `run: docker compose down -v` — runs unconditionally (even after failures or cancellation), stopping and removing the containers and, because of `-v`, also removing the named volumes (i.e. wiping `pgdata`), leaving the runner clean for the next job.

## load-test.js

This script is a standalone load-testing tool (not part of the running application) that uses the `autocannon` library to hammer the log-ingestion endpoint with concurrent, batch-shaped HTTP POST requests and report both raw throughput and derived logs/sec. It's meant to be run manually against a locally running instance of the service (e.g. `BATCH_SIZE=500 CONNECTIONS=8 DURATION=20 node load-test.js` while `docker compose up` is active) to gauge how `/logs` performs under realistic ingestion load. This replaces an earlier version of the script that sent one log per HTTP request — that shape caps throughput at the HTTP layer rather than the actual ingestion path, so the reported numbers understated what the service could really do; env-var-configurable batches fix that.

- **Line 1**: `import autocannon from "autocannon";` — imports the default export of the `autocannon` load-testing library (installed as a devDependency in `package.json`).
- **Lines 3-5**: `BATCH_SIZE`, `DURATION`, `CONNECTIONS` are all read from environment variables via `parseInt(process.env.X || "default", 10)`, defaulting to `200`, `20` (seconds), and `20` respectively if unset — this is what makes the script configurable per-run without editing the file, e.g. to compare a "many small batches" profile against a "fewer, bigger batches" profile.
- **Lines 7-20**: `makeBatch()` builds one `{ logs: [...] }` JSON string containing `BATCH_SIZE` log entries: each entry cycles `level` through `["debug", "info", "warn", "error"]` and `service` through `["checkout", "auth", "inventory", "billing"]` by index (`i % 4`), giving a realistic spread of levels/services rather than every entry being identical; `message` is `` `load test log entry ${i}` ``, and `attributes` includes a synthetic `user_id`, a fixed `region: "eu-west"`, and `retries: i % 5`. `timestamp` uses a single `now = Date.now()` captured once per batch (line 9), so every entry within one batch shares the same timestamp rather than drifting across the loop.
- **Line 22**: `const body = makeBatch();` — the request body is built **once**, up front, and reused for every request of the run (unlike the old version's `setupClient`/`client.on("request", ...)` pattern, which regenerated the body per-request). Since the goal here is throughput under realistic *shape* and *size*, not perfectly fresh timestamps on every single request, building the body once avoids paying JSON-serialization cost on autocannon's hot path.
- **Lines 24-26**: logs the run's configuration (`Ingesting: batch size ${BATCH_SIZE}, ${CONNECTIONS} connections, ${DURATION}s`) before starting, so console output from different runs is self-describing.
- **Lines 28-34**: `autocannon({ url: "http://localhost:8080/logs", method: "POST", duration: DURATION, connections: CONNECTIONS, headers: { "Content-Type": "application/json" }, body })` — invokes autocannon with the env-var-driven `duration`/`connections` and the pre-built `body`, targeting the ingestion endpoint (matching the `EXPOSE 8080`/port mapping seen in the Dockerfile and Compose file).
- **Lines 35-43**: `.on("done", (result) => { ... })` fires once the run completes:
  - **Line 36**: `reqPerSec = result.requests.average` — the average HTTP requests/sec autocannon achieved.
  - **Line 37**: `logsPerSec = reqPerSec * BATCH_SIZE` — the derived metric that actually matters for this service: since every request carries a full batch, requests/sec alone understates throughput by a factor of `BATCH_SIZE`.
  - **Lines 38-40**: prints both the raw requests/sec and the derived logs/sec (rounded via `.toFixed(0)`), labeling the latter explicitly as `requests/sec * batch size` so the two numbers are never confused when read out of context.
  - **Line 41**: prints `result.latency.p97_5` labeled as "Latency p95 (nearest bucket to p95)" — autocannon doesn't expose an exact p95 field, so this reuses the same "closest available bucket" approximation as the earlier version, just without the Arabic comment.
  - **Line 42**: prints `result.non2xx` and `result.timeouts` — new compared to the earlier version, surfacing whether any requests failed or timed out during the run, since a throughput number alone can hide a run where a chunk of requests silently errored.
